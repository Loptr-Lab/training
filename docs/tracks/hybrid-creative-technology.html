Hybrid creative-technology track

Work tasks

Combine code, interactive media, audio, video, design, automation, documentation, and production coordination into an integrated workflow.

Required capabilities

  • Interoperability across the selected tools and file formats
  • Enough compute, memory, storage, and ports for the most demanding concurrent workflow
  • A consistent accessibility layer across capture, creation, review, and delivery
  • Versioning and provenance that distinguish source, generated, edited, approved, and published material

Plan

Map the workflow stage by stage. Do not simply combine the preferred specifications from every other track. Identify the real concurrency, bottlenecks, handoffs, and accessible fallback paths, then test a representative end-to-end project.

Understanding Your AT Protocol Identity

Goal: explain the difference between a handle and a decentralized identifier (DID). No programming, account, installation or live network lookup is needed.

  1. Handle: a readable, domain-shaped account name. Interfaces often display it with an @; the underlying handle has no @. A handle can change.
  2. DID: a persistent account identifier beginning with did:. It identifies an account, not a verified real-world person.
  3. Read the fictional lookup: input handle example.test → output DID did:plc:example123. Think of this as reading a prepared lookup result, not executing a Shortcut. Both values are instructional placeholders, not resolvable accounts; the DID is not a valid production identifier.
  4. Name the two values: which is the handle, and which is the fictional DID? Explain what you learned from the mapping.
  5. Check the limit: successful resolution does not independently verify someone's real-world identity. In real protocol validation, the current DID document must also link back to the handle; this static example does not perform that check.

For the underlying rules, see the official handle specification and DID specification. A stable DID can help separate account identity from a changeable handle or hosting location; portability depends on the DID method and supported migration procedure. No account is moved or backed up by this lesson.

Check your understanding

In the fictional result above, identify the handle and DID. Does the lookup alone establish the account holder's real-world identity?

Reveal the answer and explanation

Handle: example.test. Fictional DID: did:plc:example123. No: the mapping links account identifiers; it does not prove a person's real-world identity.

Self-check: you can name each identifier and explain this limitation. If you reversed them, remember that the DID begins with did:. Re-read and try again at your own pace.

Review, feedback and revision

  1. Prepare: Download the creative-production review record. Open the mapped original rubric. Record the lesson URL, objective, audience, completion requirements, medium and accessibility adaptation before starting. Use original or permission-cleared assets. Note versions and AI-assisted steps.
  2. Make and review version 1: save the editable artifact and a viewable example. Cite a frame, timestamp, node or explanation for every mapped category. Use original source levels where provided; for UTS record qualitative feedback. No combined score or invented pass mark.
  3. Get feedback: self-assessment is the default. A peer or instructor may add a separate review, identifying their role. Retain disagreements and evidence; do not overwrite the self-review or present informal feedback as verified grading.
  4. Revise: name a specific change and how it addresses feedback. Keep both versions. If evidence is missing, identify what you need to produce or study instead of guessing a score.
  5. Review version 2: use the same categories and source descriptors. Record changed evidence and remaining limitations. These two human review rounds neither consume nor reset the separate two-attempt AI Literacy assessment.
  6. Save and resume: edit and save the downloaded record after each review. Reopen it to confirm changes before closing. Back up it and the project files. This static page does not collect inputs or autosave. Where the existing Creative Filing Library is available, its Markdown import retains this as legacy text; it does not score creative work. The Library may not be available on your version of the training site.
  7. Share if you choose: use the existing PIXIE/GitHub evidence workflow. Check rights, attribution and public visibility first. Keep private records out of public checkpoints. No new tracker, enrollment, certification or project acceptance.
